01

Security & sessions

8 findings · 4 × P0

This is where the highest-leverage work is. The platform moves real crypto but a leaked token lives for seven days, pre-2FA tokens are accepted by protected routes, and every security alert email is silently dropped.

P0SEC-1

Sessions cannot be revoked — a stolen 7-day token is unstoppable

What
verifyToken (server.js ~L1624 and middleware/auth.js) only checks signature + expiry. Tokens are issued with expiresIn: '7d'. There is no jti, no denylist, no session table, no token-version column.
Impact
A token captured via XSS, a shared device, a proxy log, or a leaked backup grants full account + wallet access for up to 7 days. Logout does nothing server-side. A password reset does not invalidate existing sessions. There is no "sign out everywhere".
Fix
Add a session_version (int) column to users; embed it in the JWT; reject in verifyToken when it does not match. Bump it on logout, password change, 2FA change, and admin force-logout. Drop access-token lifetime to 15–30 min and add a rotating refresh token stored server-side. Ship the session_version check first — it is a few lines and closes the worst of it.
P0SEC-2

Pre-2FA temporary tokens are accepted by protected endpoints

What
Login issues a { userId, pending2FA: true } token (10-min) after password success but before the 2FA code. verifyToken sets req.userId from any validly-signed token and never inspects pending2FA. Only the 2FA-verify route (server.js ~L2432) checks the flag.
Impact
For 10 minutes after entering only a password, that token can call wallet, trade, and profile endpoints. 2FA is effectively enforced only in the login UI flow, not at the API.
Fix
In verifyToken and optionalAuth: if (decoded.pending2FA) return res.status(401). Only the 2FA-completion route may accept that token. One-line change, high value.
P0SEC-3

Login lockout & security logging are dead in production

What
The security_events table does not exist in the live database. services/securityLogService.js catches the missing-relation error and becomes a no-op with a console warning. Failed-login tracking, per-account lockout, and suspicious-activity logging all silently do nothing.
Impact
The only brute-force defence is the 10-requests / 15-min per-IP rate limiter — trivially bypassed with rotating IPs or a botnet. No record exists of credential-stuffing attempts. No forensic trail after an account takeover.
Fix
Run database/security_events.sql in the Supabase SQL editor. Verify writes succeed. Add per-account lockout (e.g. 5 failures → 15-min lock, escalating) keyed on user id, not IP. Alert on lockout events.
P0SEC-4

Every security & fund-safety alert email is silently dropped

What
alertOpsOfCreditFailure (both deposit monitors) and the SYNC_FAILURE reconciliation alert send via nodemailer service:'gmail' using EMAIL_USER / EMAIL_PASS. Neither variable is set — the platform uses SMTP_* (Brevo) and Resend everywhere else. Every send throws and is caught-and-ignored.
Impact
Real incidents reached no one: failed on-chain deposit credits, and a Supabase outage mid–CEO-withdrawal on 2026-08-28 08:06 UTC that wrote a SYNC_FAILURE flag. The team is blind to the exact events that most need a human.
Fix
Point all alert paths at the working Brevo/Resend transport (shared helper). Add a daily "alerts channel healthy" heartbeat so a broken pipe is visible.
P1SEC-5

2FA login state lives in a process-memory Map

What
pending2FALogin (server.js L70) is an in-memory Map. It is wiped on every restart / deploy and is not shared between instances.
Impact
A restart mid-login forces users to restart the flow. If the backend ever runs more than one instance (autoscale, blue/green), the 2FA code check lands on an instance that never saw the code — the flow breaks or, depending on routing, can be skipped.
Fix
Move to a short-TTL table (pending_2fa_sessions) or Redis, keyed by the temp-token id, with a DB-side expiry.
P1SEC-6

NODE_ENV=development is set in production

What
Live .env has NODE_ENV=development plus START_SERVICES=true to force the monitors on.
Impact
Express serves verbose errors and stack traces to clients. The CORS layer's origin.startsWith('http://localhost') bypass is active in production. Any other NODE_ENV !== 'production' branch behaves in dev mode.
Fix
Set NODE_ENV=production. Re-verify the deposit-monitor / sweep / integrity start guard still fires (it also honours START_SERVICES, so it will). Remove the localhost CORS exception or gate it on an explicit ALLOW_LOCALHOST flag.
P1SEC-7

Uncommitted rateLimit.validations = {} is live in production

What
server.js ~L311 — a working-tree edit, not in git — disables express-rate-limit's internal config validation.
Impact
It silences the warning that would fire if trust proxy is misconfigured. With the wrong proxy count, the limiter keys on a client-spoofable X-Forwarded-For (rate-limit bypass) or on a single upstream IP (every user throttled as one).
Fix
Remove the line. Confirm the platform sits behind exactly one proxy so app.set('trust proxy', 1) is correct; fix properly if not. Commit whatever remains.
P2SEC-8

SECURITY DEFINER money RPCs are only partly hardened

What
praqen_credit_deposit, praqen_internal_transfer, praqen_reject_withdrawal set search_path = public, pg_temp (good) but not the stronger search_path = '' with fully-qualified public.*. The idempotency key is a caller-trusted string, never checked against p_user_id / p_amount / p_currency. Postgres CHECK treats a NULL result as satisfied, so a NULL balance passes every sanity bound.
Impact
Defence-in-depth gaps on the functions that move every deposit, transfer, and refund. Low likelihood, maximum blast radius.
Fix
SET search_path = '' + schema-qualify all references. Derive or validate the idempotency key from the operation's own fields. Add NOT NULL to wallets.balance_btc / balance_usdt / locked_* if absent.
02

Deposits & funds

4 findings · 1 × P0

Automatic crediting works again for deposits arriving after the late-August cutover. Earlier deposits, and any the monitor misses, still depend on a manual step.

P0FND-1

Real on-chain deposits from the Aug 25–28 window are still uncredited

What
praqen_credit_deposit only reached production around 27–28 Aug; deposits before that were detected but never credited, and the hourly reconciliation service was un-wired dead code until 28 Aug (and is still flag-only).
Confirmed owed
kingkong79-Pro — 0.01174822 BTC, tx fc0e94bf…, arrived 10:44 UTC, swept to the hot wallet 13:16, zero ledger rows. king888 — ~0.0348 BTC across 3 flags, status ambiguous (credited pre-Aug-27 then reversed — needs an on-chain trace). Plus any other UNCREDITED_ONCHAIN_DEPOSIT rows in reconciliation_flags.
Fix
One reviewed back-fill script (follow the existing correct-*.js convention): walk every address, and for each confirmed on-chain arrival with no deposit_tracking_v2 row and no wallet_transactions row, credit it through praqen_credit_deposit with an audit note. Adjudicate the reversed-then-reflagged cases by hand before running. Never ad-hoc UPDATE.
P1FND-2

Reconciliation service detects misses but never credits them

What
depositReconciliationService.js is Phase A: it writes UNCREDITED_ONCHAIN_DEPOSIT flags hourly and stops. Every miss needs a human to notice and credit.
Impact
Time-to-credit for a missed deposit is "whenever someone reads the flags table" — in practice, when the user complains.
Fix
Build Phase B: auto-credit from a flag when the txid is confirmed on-chain, absent from both deposit_tracking_v2 and wallet_transactions, and within sane amount bounds — through praqen_credit_deposit, with an audit row. Escalate (working email now) anything it can't resolve.
P1FND-3

USDT deposit monitor is falling behind its own cycle

What
~1,524 Tron addresses scanned sequentially at 550 ms each ≈ 14 min per pass, against a 90-second timer — logs show Previous cycle still running — skipping. No USDT auto-credit in deposit_tracking_v2 since 01:21 on audit day; yornnguyen's USDT needed a manual credit.
Impact
USDT deposits can wait 15+ minutes, or be missed if TronGrid rate-limits mid-pass. Detection latency is effectively unbounded under load.
Fix
Confirm from live logs whether passes complete. Then: shard the address set across workers, or pull recent account events from TronGrid once and only scan addresses with activity, instead of polling every address every pass. Emit a "last full cycle completed" metric and alert if it stalls.
P2FND-4

14 users have no Tron deposit address

What
user_wallets.tron_address is null/empty for 14 users (was 11 — growing). Address provisioning is missing on some signup paths.
Impact
Those users' USDT deposits are invisible to the monitor — funds arrive on an address nothing watches.
Fix
Run backfill-tron-addresses.js (review its dry-run output first). Gate the "Deposit USDT" UI behind a provisioned address and retry provisioning on failure.
03

Swap

2 findings · 1 × P0

BTC → USDT swap is not broken code — it is switched off because the Tron hot wallet cannot pay out the USDT it would owe.

P0SWP-1

BTC → USDT swap disabled — Tron hot wallet is out of gas

What
BTC_TO_USDT_SWAP_DISABLED=true in .env; the endpoint (server.js L13397) returns HTTP 503 before any swap logic. The swap itself is a pure internal ledger move — the block is a liability-control measure.
Root cause
Hot wallet TXeSskzYJnbaNwg6sJvkYsgUPss7hkzYUY holds 15.34 TRX (reserve floor 100; one USDT withdrawal needs ≥30). Status critical. 2 USDT sweeps stuck. Company USDT wallet ≈ $0. USDT owed to users: $2,297.51 available + $600 locked.
Fix
1. Fund the hot wallet with 300–500 TRX. 2. Verify its USDT balance covers the ~$2,300 liability; top up if short (sweeping user deposit addresses will also refill it once gas is back). 3. Set BTC_TO_USDT_SWAP_DISABLED=false and restart. Pending sweeps auto-retry. No code change needed to re-enable.
Harden
Alert when TRX < MIN_TRX_RESERVE. Replace the static env flag + restart with a live check that auto-disables/enables this swap direction on hot-wallet health. Auto-refill TRX.
P2SWP-2

Swap fee rate disagrees with itself

What
The endpoint response says fee_pct: '1%', the swapService.js header comment says 0.2%, the code is SWAP_FEE_RATE = 0.004 (0.4%). Users are charged 0.4%.
Fix
Decide the real rate once; align the constant, the endpoint field, the header comment, and any UI copy.
04

Trading & reputation

3 findings · none P0

Counters that traders rely on to judge a counterparty are seeded, inconsistently updated, and half-migrated. Not a fund risk — a trust risk.

P1TRD-1

total_trades stops moving on several completion paths

What
Only POST /api/trades/:id/release calls updateUserTradeStats. Dispute-resolved completions (resolveDispute, server.js L9102 / L9166) never increment. tradeEscrowService.updateTradeStats() is dead code. Counters are large seeds (e.g. one account: total_trades 77,790 vs 931 real completed), so a naive recompute would freeze everyone.
Impact
Traders finishing deals via dispute resolution see their trade count stuck. Reputation understated.
Fix
First check in Supabase → Database → Triggers whether on_trade_completed / on_review_created_update_feedback still exist. If removed: add updateUserTradeStats(buyer_id) + (seller_id) after every COMPLETED transition, dispute path included; keep the +1 model. If present: the triggers already cover it — investigate the specific report instead. Do not run fix_duplicate_counting.sql — it resets every seeded counter.
P2TRD-2

Migrated P2P feedback doesn't show consistently

What
Migrated traders carry a verified count in positive_feedback / total_feedback_count, but p2p_migrated_feedback (the badge string) is blank and the profile's Feedback tab counted only on-platform reviews rows.
Status
Front-end display fix is staged locally (Feedback tab, badge, empty states, and the Weekly Stars card now read total_feedback_count). Not deployed.
Fix
Ship the staged front-end change. Run a one-time UPDATE users SET p2p_migrated_feedback = total_feedback_count::text WHERE p2p_migrated_platform IS NOT NULL AND COALESCE(p2p_migrated_feedback,'')=''. Patch PUT /api/admin/p2p-migration/:id/approve to write the string going forward.
P2TRD-3

Weekly Stars table is half-migrated — admin picks silently fail

What
trader_of_week is missing the stats_snapshot column its code writes, so both the admin "Pick a winner" action and the auto-rotation job throw on every upsert. The public banner also showed 0 / 0 feedback because the row carries no feedback columns.
Status
Staged locally: getCurrentWinners() now enriches each winner from users; banner title changed to "Traders of the Week"; rotation set to 24h. Not deployed.
Fix
Run ALTER TABLE trader_of_week ADD COLUMN IF NOT EXISTS stats_snapshot JSONB; (and pin_expires_at TIMESTAMPTZ). Ship the staged enrichment. Optionally delete legacy category LIKE '%:%' rows.
05

Ops & resilience

8 findings · none P0

The recurring theme across the whole audit: single points of failure with no alerting and no automated recovery. Every incident so far was caught by a user, not a monitor.

P1OPS-1

Balance mirrors drift on every escrow event

What
Three balance stores — wallets (authoritative), user_balances, user_wallets.balance_btc. praqen_credit_deposit was patched to sync the BTC mirror on deposit, but escrow release / refund / trade-settlement still write only wallets — ~62 drift events/day, 539+ open MIRROR_DRIFT flags.
Impact
Any read path that trusts a mirror shows a wrong balance. A past ad-hoc SQL correction that left a mirror high enabled a ~697 USDT swap-out exploit before it was caught.
Fix
One AFTER UPDATE trigger on wallets that mirrors balance_btc/balance_usdt into both secondary tables — covers every writer at once. Then reconcile and clear the flag backlog. Longer term, demote user_balances / user_wallets to views over wallets.
P1OPS-2

Deposit detection rides on public block explorers with no retry queue

What
BTC detection depends on mempool.space + blockstream.info. Logs are full of All APIs unreachable, DNS failures, and 429s. A failed poll is not retried — the next cycle just re-reads from scratch.
Impact
A sustained explorer outage during a deposit's arrival→sweep window is a permanent miss (mitigated now by txid tracking + reconciliation, but reconciliation is still flag-only — see FND-2).
Fix
Add a third source (BlockCypher is already a fallback elsewhere) and/or run an own Esplora/Electrum node or a paid webhook feed. Persist a "needs a successful check" set so a failed poll is retried, not dropped.
P1OPS-3

Hot wallets have no balance / gas alerting

What
The Tron hot wallet drained to 15 TRX with nothing flagging it (see SWP-1). No alert exists for low TRX, low hot-wallet USDT, or low BTC hot-wallet balance vs liabilities.
Impact
Withdrawals and swaps fail before anyone knows the wallet needs funding. Recovery only starts after user complaints.
Fix
A scheduled check on every hot/company wallet: TRX vs reserve, USDT/BTC vs summed user liability. Alert (working email now) at warning and critical thresholds.
P1OPS-4

No test suite on money-moving code

What
npm test is exit 1. The atomic RPCs are covered only by two hand-run .sql files, and there is no record they were ever executed against the live schema.
Fix
Minimum viable: run the RPC test SQL in CI against a throwaway Supabase branch on every PR. Add integration tests for deposit-credit idempotency, swap both directions, escrow release, and withdrawal approve/reject races.
P2OPS-5

No automated treasury rebalancing

What
Swaps accumulate whatever BTC/USDT imbalance users create. Nothing moves value between the BTC hot wallet and the Tron hot wallet to keep both solvent — the gas crisis is a downstream symptom.
Fix
A scheduled treasury job: watch both hot wallets against liabilities, alert or auto-convert when either side falls below a floor.
P2OPS-6

The wallets table has no schema in version control

What
Created directly against production. No CREATE TABLE in the repo. UNIQUE(user_id) exists only if the 2026-08-25 migration ran.
Impact
A fresh environment cannot be stood up from the repo. Real constraints / defaults / NOT NULLs are unknown to anyone reading the code.
Fix
Introspect the live schema, commit it as a migration, and verify the unique constraint and NOT NULLs are actually present.
P2OPS-7

Deposit-confirmation emails to users also fail

What
Same EMAIL_USER/EMAIL_PASS gap as SEC-4 — the user-facing "deposit received" email throws and is swallowed. In-app + push + Telegram still fire.
Impact
A slow credit feels like a lost deposit because the one channel users check for money movement is silent.
Fix
Route the deposit emails through the working transport alongside the SEC-4 fix.
P2OPS-8

Stale startup log lines misreport monitor intervals

What
Startup logs say the BTC monitor "polls every 5 min" and USDT "every 15 min"; the actual constants are 15 min and 90 seconds.
Fix
Cosmetic — log the real constant values. Low effort, prevents wrong assumptions during incident triage.
Suggested sequencing. Week 1 — SEC-2 and SEC-1's session_version check (hours of work, closes the account-takeover window), SEC-3 and SEC-4 (run one SQL file, fix one transport), FND-1 back-fill, SWP-1 wallet top-up. Sprint 2 — OPS-1 mirror trigger, FND-2 Phase B, FND-3 throughput, TRD-1 after the trigger check, OPS-2 / OPS-3 / OPS-4. Backlog — everything marked P2. None of it requires a rewrite; most P0/P1 items are contained changes to one file or one migration.
